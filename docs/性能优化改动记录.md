    - **`lib/push-outbox-client.ts` — 换掉失效的过期判定**：原判定要求「存在 createdAt 晚于 `armAt` 的 assistant 消息」，但冷场重连/定时唤醒的 `armAt` 写的是**未来的触发时刻**，用户在触发前几小时的回复永远不满足，废单畅通无阻。现改为比对 `preMergeSessionBaseline`（本轮 `consumeServerOutbox` 开始时冻结的各会话基准，每轮开头 `clear()`）与 `snapshotLastUserMsgId`；没有基准的老单用 `armedAt` 兜底。**必须用冻结基准而非实时读取**，否则连发第 1 条落库后，第 2、3 条会把刚插入的消息当成「本地已往前走」的证据而被全部误杀。
    - **本地幂等记忆**：新增 `consumedOutboxIds`（上限 200）并持久化到 `localStorage` 的 `ai_phone_consumed_outbox_ids_v1`。ack 是网络请求，失败时条目留在服务端、5 分钟后被再次拉回；没有这层记忆时同一条会被反复 `parseAndSaveResponse` 插进聊天记录，表现为「零碎地凭空多出几条」。持久化是为了覆盖「ack 失败后用户刷新/重开 App」的场景。
    - **全局生成锁真正接通**：`lib/generation-lock.ts` 此前只有 `hasActiveGenerationLock()` 的调用方（`memory-summarizer.ts`），没有任何地方调 `beginGeneration()`，计数恒为 0，那道退避一直是失效的。现于 `lib/chat-engine.ts` 的 `generateChatCompletion` 与 `lib/group-chat-engine.ts` 的 `generateGroupChatCompletion`（后者拆出 `generateGroupChatCompletionInner` 以便整体 try/finally）中成对调用 `beginGeneration()` / `endGeneration()`，使长期记忆总结与离线快照组装在真实生成期间 100% 退避。

29. 第 27、28 条整体废弃：生成链路与离线预约链路已还原至官方原版（11-04 基线）。原因与教训如下。
    - **起因**：第 26 条之前（即 v16 之前）系统除「生成消息略卡」外功能正常。此后从 v17 到 v24 连续叠加十余轮改动，先后引发：生成时「卡 1～2 秒 → 不卡 → 再卡」的循环、点暂停显示已暂停却仍在生成、退出重载后两三秒消息自动蹦出、开机箭头不显示需重启手机。每轮改动单独看都「有理有据」，叠加起来却把链路改成了无法定位的复合故障。
    - **教训一：不要在已经叠了多层私改的链路上继续加定时器与重试**。v24 加的 `scheduleIdleBailoutRefresh`（15 秒防抖 + 10 秒重试 3 次）与 `refreshScheduledBailouts` 的 2.5 秒间隔循环，在全量提示词组装的量级下，恰好把「卡一下」放大成「卡—不卡—卡—不卡」的周期性卡顿。而让这套循环真正生效的，是同一次提交里刚接通的全局生成锁。
    - **教训二：`hasActiveGenerationLock` 长期是死代码**。`generation-lock.ts` 自建立起只有调用方没有 `beginGeneration()`，计数恒为 0。任何基于它的退避逻辑在接通前都不会生效，接通后会突然改变全部后台任务的行为——这类「隐形开关」在改动前必须先确认它是否真的在工作。
    - **教训三：删除定义必须同步清理全部调用，删除调用必须同步清理 import**。本轮多次出现「删了 `resolveShortTermMaxMessagesPerSession` 定义却留着 4 处调用」「删了 import 却留着函数体调用」的情况，每一次都会让整个项目在构建时失败。
    - **教训四：`edit_item` 的 find 片段中严禁写省略占位符**（如 `// ... (省略部分注释)`）。这类占位符永远匹配不到原文，会导致「工具返回成功但文件根本没改」，而后续汇报会误以为已生效。
    - **教训五：跨轮中断或取消提案后，暂存区已重置**。必须在同一轮内重新补齐全部待改文件，并核对提案卡片包含的文件个数。本轮曾出现过「9 个文件的提案里漏了 5 个已撤回的文件」的情况。
    - **后续处理**：上述文件当时确实一度还原至官方原样，但后续排查证明「还原」并不能解决闪退——真正的死因是主线程饱和与内存基线，于是又基于官方基线做了减法性质的定点修复，见下方第 30～41 条。现在这些文件是「官方基线 + 定点减法」，不是纯官方原样，也不是当年叠了十几轮的复合私改。
    - **保留项**：`lib/short-term-assembler.ts` 的 `prepareShortTermContext` 保留单趟 `bucket` 分桶（等价于约 20 次 `timeline.filter`，纯减少遍历次数、不改变输出）；开屏水合优化、API 列表排序（`api-groups.ts` 等）、保活音频不抢系统音频焦点（`use-weixin-bridge.ts`）也一并保留。

    - **现象**：小坊上下文上限总是自己变回 1000000。
    - **病因**：根因不在默认值写死，而在**存储位置**——`ai_phone_qa_context_budget_chars`（`lib/qa-chat-store.ts`）与 `ai_phone_qa_page_chars` / `ai_phone_qa_max_output_tokens` / `ai_phone_qa_max_rounds`（`lib/qa-prefs.ts`）这四项此前只写裸 `localStorage`，既没有 IndexedDB 副本可恢复，也没有在 `lib/data-management/modules.ts` 的主模块登记。于是它们落进 `cache` 模块的 `includeAll` 范围——用户点一次「缓存与未分类数据 → 清理」，或恢复一份不含缓存的备份，四项设置连同其它遗留键一起被删，下次读取直接回落到默认值。
    - **改法**：`lib/qa-prefs.ts` 新增 `readPref` / `writePref` 两个小助手（`kvGet` 优先、`localStorage` 兜底），四项全部改走 kv-db，并对各自的键调用 `registerKvMigration` 迁移旧值；写入改 `kvSet`、恢复默认改 `kvRemove`。`lib/qa-chat-store.ts` 的 `getContextBudget` / `setQaContextBudgetChars` 同样改走 kv-db + `registerKvMigration`，并保留 localStorage 兜底读。`lib/data-management/modules.ts` 把四个键登记进 `settings` 主模块的 kv `keys`。
    - **缺一不可**：只迁 kv-db 而不登记，`cache` 模块照样会把它们扫进清理范围；只登记而不迁，旧值仍然只有 localStorage 一份副本。
    - **不要顺手改 `emit`**：`setQaContextBudgetChars` 末尾必须保持 `emit()`——`contextUsage` 是「已用 / 预算」的比值，必须按新分母重算才会更新进度条，传 `emit(true)` 会沿用旧比值导致保存后百分比不动。

42. 顶栏实时模糊与常驻合成层是生成卡顿与闪退的 GPU 侧真凶：
    - **现象**：生成时屏幕上方概率出现一块 iOS 磨砂质感遮罩，工坊名字、清理工具、调用记录、对话记录、返回那排按钮全被糊成灰色；新开空对话也是点暂停迟钝一秒；生成途中偶发闪退，且 `env_check` 的 `errors` 一条报错都没有（进程被系统直接杀掉，JS 层来不及抛错）。
    - **病因**：`backdrop-filter` 在 iOS WebKit 上是真实栅格操作，元素背后有任何东西在动，它就必须每帧重新快照并模糊一次。而工坊顶栏同时叠了六层：`styles/qa.css` 里铺满全宽、还向下多探 30px 再叠 `mask-image` 的 `.qa-header::before`（`blur(12px)`）＋名字胶囊 `.qa-header-center`（`blur(16px) saturate(1.5)`）＋四个 `.qa-icon-btn`（同款 `blur(16px) saturate(1.5)`）。生成期间正下方又有 `.qa-thinking`（1.6s）与 `.qa-cursor`（1s）两个 `infinite` 闪烁动画持续驱动重采样。全站共享的 `styles/components.css` 的 `.page-header` 另挂着 `blur(20px) saturate(180%)` 加 55% 半透明底，所以聊天室与其它 App 页面同样中招——这就是「无论在哪个窗口都会出现」的原因。再叠上 `styles/qa.css` 的 `.qa-stage` 与 `styles/phone-shell.css` 的 `.phone-swipe-layer` 两处常驻 `will-change: transform`，整页被永久锁成 GPU 合成层，显存压力翻倍。GPU 纹理池见底时模糊层就退化成整块灰磨砂，合成器队列塞死导致点击排队（点暂停迟钝），再顶穿配额即被 Jetsam 杀进程。
    - **改法**：`styles/components.css` 的 `.page-header` 去掉 `backdrop-filter` 与 `-webkit-backdrop-filter`（都置 `none`），底色由 55% `color-mix` 改为不透明实色 `var(--c-header-bg, var(--c-page-body-bg, #ffffff))`；`styles/qa.css` 的 `.qa-header::before` 删掉两层 `backdrop-filter`、改填 `var(--qa-bg-canvas, #fafaf7)` 并保留 mask 渐变（那里原注释本来就写的「非毛玻璃」，实现与设计意图背离）；`.qa-header-center` 与 `.qa-icon-btn` 删掉两层 `backdrop-filter`，底色提到 `rgba(255, 255, 255, 0.94)`；`.qa-thinking` 与 `.qa-cursor` 删除 `infinite` 动画，改为静态呈现；`.qa-stage` 与 `.phone-swipe-layer` 的常驻 `will-change: transform` 删除，只保留 `.phone-swipe-dragging` 拖拽期间生效。
    - **边界**：本轮是纯 CSS 减负，不动任何 JS 逻辑，因此可解决「生成时顶部磨砂 / 点暂停迟钝 / 生成中闪退」这一组；但治不了「点完发送、字还没吐之前那一两秒」的提示词组装 CPU 开销，也治不了 `chat-db` 启动全量常驻内存带来的整体变钝。

### 教训

7. **「还原至原版」是最危险的操作，必须逐调用点核对**。曾出现过声称还原、实际留下四处未声明标识符（两处在离线回传、两处在群聊组装）的情况，全部只在运行时才炸，构建期毫无提示。删任何声明前，先全库搜调用点，删完再搜一次确认归零。
8. **「立刻监听」和「定时巡检」是两件事，绝不能一起否定**。定时巡检（每 1.5 秒一次的 `setInterval`）在生成与多轮工具调用期间持续抢主线程，闭包还会把 `llmMessages` 钉到本轮之后——这是必须砍掉的部分。但「进入生成就立刻挂一次性空壳监听」本身是对的：不挂就会让生成初期切后台彻底丢兜底。正确组合是立刻挂、前台零克隆、切后台瞬间才构建上传、完成后立刻摘掉，四件事缺一不可。
9. **防抖时长要按真实用户节奏定，不能只为「不阻塞当前帧」**。8 秒防抖在正常打字节奏下形同虚设（每条消息后都会触发一次），必须放宽到远超人类操作节奏的量级（45 秒），并叠加「正在生成/页面隐藏」双守卫。
10. **Service Worker 的 activate 必须「先建立新的安全兜底，再清理旧的」**。任何「先删后拉」的顺序在网络失败时都会把用户推进无缓存深渊，且 `catch` 吞掉失败会让问题完全静默。现行的 activate 是「先确认新桶里确实有 `/`，再清理旧桶；拿不到就保留旧桶等下次激活重试」，不会出现新旧桶同时为空导致根导航失败的白屏。
11. **决定首帧正确性的数据不能靠超时放行空值**。异步读不到时，「等」和「放行空值」是两种代价完全不同的选择：`DesktopShell` 首帧拿到空 `assets` 会渲染白底 + 默认图标，等异步回调到了再替换，也就是每次启动都闪一下白底；而选择等，最坏只是偶发开屏偏慢。对这类数据必须宁可等，超时兜底只适用于非首屏、可降级的读取。
12. **指纹缓存/内容哈希类「跳过上传」优化，救不了组装开销**。若指纹比对排在组装之后，它只省网络流量；真正的开销在组装本身，必须靠防抖与守卫来控制触发频率。
13. **用户可调的设置项不能只写裸 `localStorage`**。「缓存与未分类数据」模块是 `includeAll` 的兜底清理器，任何没在主模块登记的键都会被它扫走；而 localStorage 本身在 iOS 上也没有 IndexedDB 那样的持久化保障。凡是用户能在界面上调的项，一律走 kv-db + `registerKvMigration`，并在 `lib/data-management/modules.ts` 的主模块里登记键名——两件事缺一不可，只做一半仍然会丢。
14. **`requestAnimationFrame` 不能单独当作「让出一帧」的同步点**。页面一进后台，iOS 会冻结 rAF 回调，只靠 rAF 的 `await` 会永久挂起，把整条流程卡在中间状态（生成中、忙碌标志不复位）。凡是跨越「用户点完立刻切后台」这个窗口的让帧等待，都要配一个 `setTimeout` 兜底出口。
15. **分析性能问题必须先分清「主线程饱和」与「内存被杀」**。二者的体感都是「卡」和「闪退」，但证据完全不同：主线程饱和时点击排不进事件循环（按钮没反应），内存被杀时进程直接消失且 JS 层无任何报错（`env_check` 的 `errors` 为空就是信号）。看到「点某个按钮就闪退」时，必须先向用户确认按钮到底有没有点上——没点上说明触发源是卡顿本身，把矛头指向那个按钮的点击处理函数会从头错到尾。
16. **`getComputedStyle` / `getBoundingClientRect` 绝不能放在高频回调的节流门槛之前**。它们会强制同步重排，而流式回调是每秒几十次的热路径。正确的顺序永远是「先做廉价的布尔与时间判断，最后才做可能触发布局的 DOM 查询」。
17. **凭 commit 说明无法判断哪一版最稳，也不应把「还原到某个版本」当作修复手段**。用户报「一直卡」时，说明这不是某版引入的回归，而是长期累积的开销；这类问题只能靠确定性减法定位，逐个消掉有实证的开销点。
18. **已有的存储能力要先查再用**。`mediaRef` 与 `dataUrl` 在生图返回里是并行字段，系统自带的媒体维护也一直在把 `mediaUrl` 写成 `media-store://`，说明轻量引用路径早已打通；把几 MB 的 base64 直接落库属于绕开了既有能力。

## 三、 绝对不能碰的架构红线

1. **严禁卸载 `phone-chat-app.tsx` 的 `visitedSessions` 常驻聊天室**（否则进房闪白屏、`<ChatPluginSlot>` 反复重建卡死聊天 JS 插件）。
2. **严禁改动 `chat-room.tsx` 顶层 `<div ref={wrapperRef}>` 结构与 `ChatSettingsPanel` 的 `createPortal` 挂载方式**。
3. **严禁在 `chat-room.tsx` 抽离流式预览/编辑弹窗子组件，严禁给 `BilingualTextBlock` 加自定义 `memo` 比较函数**。
4. **严禁把 `desktop-shell.tsx` 的 `MiniAppWindow` 改成条件挂载，也不要把桌面改成常驻不卸载或加返回等待遮罩**。
5. **严禁给全屏根节点加 `translateZ(0)`**：切回前台只对轻量状态栏做一次唤醒重绘，整棵 `.phone-shell` 加合成层会让 WebKit 为全屏所有子元素重建巨幅 GPU 纹理，切回瞬间 Jetsam 闪退。
6. **严禁在 `document.hidden` 切后台瞬间同步组装巨型 Prompt**（扫模块时间线、世界书、正则，再双份 `JSON.stringify`）；后台任务一律先校验 `visibilityState === "visible"`。
7. **严禁建立无上限的 base64 内存缓存**，严禁把含 HTML 模板、剧场正文的整包大 State 塞进缓存；热路径只缓存轻量投影或索引。也**严禁在 `llm-prompt-assembler.ts` 引入正则结果缓存**（同一份正则在不同上下文下结果不同，缓存会让显示层与提示词层互相污染）。
8. **严禁改变 `main-app.tsx` 先拿齐完整主题资产再放行 `hydrated` 的顺序**，也不得用超时放行空 `assets`——那会让首帧白底 + 默认图标，每次启动都闪一下。
9. **严禁改动 `public/sw.js` 的 `networkFirst` 缓存优先逻辑**；更新前端代码时只允许递增第 1 行 `CACHE_VERSION`，`activate` 必须保持「先确认新桶有 `/` 再删旧桶」。
10. **严禁把 `chat-room.tsx` 进入会话时切出的首屏消息塞进异步回调**（如 `prewarmStickerCache` 的 `.then()`），必须同步立即上屏并贴底，否则首次进某个角色的聊天室会白屏 1～2 秒。
11. **严禁在前台可见时让 `chat-engine.ts` 的云端兜底克隆 `llmMessages` 或调用 `buildProviderRequest`**；也**严禁在生成开头死等固定秒数才挂 `visibilitychange` 监听**（前 15 秒切后台会彻底丢兜底），更**严禁加 `setInterval` 巡检**。正确形态：进入生成立刻挂一次性空壳监听，前台零克隆，切后台那一瞬间才构建上传，完成后由 `cancelPending` 立刻摘掉。
12. **严禁擅自改动短期记忆与首屏的条数口径**。短期记忆一律「倒序累加 Token、达预算且满 20 条即停」（`prepareShortTermContext` 与 `prepareGroupShortTermContext` 同口径），严禁放大到几百上千条远古消息；聊天室首屏与分批加载保持 20/20，工坊首屏保持 12 条；也不得擅自砍低工坊上下文预算。
13. **严禁在 `assembleNativeTimeline` 或 `buildChatPromptMessages` 中插入过多无条件 `yield` / `setTimeout` 切点**，避免把生成切成断续卡顿，或在 iOS 上制造宏任务风暴。
14. **严禁把 `assemblePromptPayload` 或 `assembleGroupPromptPayload` 改为生成器函数**——JSC 会把大局部变量装箱进堆上闭包，直接引发 OOM 闪退。
15. **严禁在 `use-weixin-bridge.ts` 中为保活音频监听 `pause` / `suspend` 后强行调 `play()` 抢系统音频焦点**，也**严禁在 `pagehide`、`beforeunload` 或组件 cleanup 中销毁已由用户手势解锁的全局音频实例**（销毁后切后台回来必重载）。
16. **严禁在 `push-bailout-client.ts` 开机 20 秒无条件全量刷新所有角色预约单**；**严禁在 `follow-up-service.ts` 的 `cancelFollowUp` 中于用户发消息瞬间同步抢跑完整提示词组装**（必须防抖）；**严禁自创后台周期性重试循环**，既浪费云端额度又制造循环卡顿。
17. **严禁在 `chat-room.tsx` 中让文字生成流程死等全部图片生成完毕才释放发送按钮**。文字落库后必须立即释放 `isGenerating`；待生成图片气泡须保留独立小叉号取消入口，并与本轮停止信号联动。
18. **严禁在 `phone-qa-app.tsx` 中仅凭 `scrollTop` 变小就解除自动贴底**。必须关闭浏览器原生滚动锚定，并配合真实触摸或滚轮手势判定用户上滑，否则初次挂载 `scrollTop` 本来就是 0，会一进页面就把全部历史灌进来。
19. **严禁把 `getComputedStyle` / `getBoundingClientRect` 放在高频回调（流式 `onStreamDelta` / `onOfflineDelta`）的节流门槛之前**。它们强制同步重排，正确的顺序是先做廉价的布尔与时间判断，最后才做可能触发布局的 DOM 查询。
20. **严禁把用户可调的设置项只写裸 `localStorage`**。「缓存与未分类数据」是 `includeAll` 兜底清理器，未在主模块登记的键会被它扫走。这类键必须走 kv-db + `registerKvMigration`，并在 `lib/data-management/modules.ts` 的主模块里登记键名，两件事缺一不可。
21. **严禁在流式更新区域的上方叠加多层 `backdrop-filter`，也严禁在祖先节点常驻 `will-change: transform`**。`backdrop-filter` 在 iOS WebKit 上必须每帧重新快照背后画面，背后一旦有滚动或无限循环动画，模糊层就会持续重采样直到 GPU 纹理耗尽——表现是屏幕出现灰磨砂遮罩、合成器队列塞死导致点击迟钝、最后被 Jetsam 杀进程（且 JS 层无任何报错）。顶栏这类常驻区域一律用不透明实色底；`will-change` 只在真正拖拽或过渡期间临时生效，绝不常驻。
