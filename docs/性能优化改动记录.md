# 性能优化改动记录（卡顿治理六项）

> 本文档按「现象 → 实测数据（测试条件与数据来源） → 根因 → 改了什么（文件:行） → 验证结果 → 遗留与风险」格式维护。动手改目标模块前先检索本文档。

---

## ① 退出应用卡 0.5–0.6s → 桌面常驻挂载 + CSS 隐藏

- **现象**：从任何应用（聊天、剧情、独家特调等）返回桌面时均卡顿 0.5–0.6s 以上。
- **实测数据**（源头仓库基准，前台 & 后台同会话 A/B，含真实导入数据）：
  - 改动前：前台「退出 → 桌面图标就绪」耗时 291–308ms（React 重挂）+ 245–289ms（首帧栅格化），单帧最长 246–343ms；后台页同会话 392–467ms。
  - 改动后：前台降至 48–66ms，单帧最长降至 23–35ms；后台页同会话降至 62–74ms。
- **根因**：`DesktopShell` 中桌面层与 App 正文采用 `{!activeApp ? <桌面/> : <App/>}` 互斥条件渲染，Dock 同样挂在 `{!activeApp}` 下。退出应用时整棵桌面树（30+ 层 `backdrop-filter` 毛玻璃 + 图标皮肤图）被卸载再重挂；同时 `.phone-wallpaper` 带有 `transition: opacity 220ms ease` 导致逐帧重模糊。
- **改了哪里**：
  - `components/desktop-shell.tsx`（约 4570–4900 行）：移除 `.phone-swipe-layer`、`.page-controls`、`.dock` 外层的 `!activeApp` 条件卸载，改为常驻挂载，统一添加 `.phone-desktop-layer` 类、`inert={Boolean(activeApp)}` 与 `aria-hidden={Boolean(activeApp)}`。
  - `styles/phone-shell.css`（第 153 行、第 1000 行附近）：`.phone-wallpaper` 的 `transition` 改为 `none`；新增 `.phone-workspace.app-open > .phone-desktop-layer` 与 `.phone-shell.app-open-shell > .phone-desktop-layer` 的 `display: none !important` 规则。
- **验证结果**：退出应用时桌面 DOM 与毛玻璃层不再重新创建，直接切换 `display` 瞬时恢复。
- **遗留与风险**：常驻后「挂 App + 摘桌面」落在同一帧，打开应用慢约 40–60ms；且 App 打开期间桌面树常驻，桌面 state 变化会连带重渲染桌面子树——若日后发现应用内操作变卡，优先排查桌面 state 订阅。

## ② 进对局卡 6–7s（第一层）：存储层整包重复解析加备忘

- **现象**：进入长轮次对局时主线程连续长阻塞。
- **实测数据**（源头仓库基准，14MB 对局库 / 31 场 / 2743 轮）：
  - 改动前：同一次进入对局触发 22 次整包 `JSON.parse`（单次 63–84ms）。
  - 改动后：重复解析从 22 次降至 1 次。
- **根因**：`lib/mixology/storage.ts` 的 `readJson` 每次调用都对 `kvGet(key)` 返回的大字符串直接执行 `JSON.parse`，而组件初始化、槽位解析、开场刷新、列表同步在同一帧内反复调用读取函数。
- **改了哪里**：
  - `lib/mixology/storage.ts`（第 73–105 行）：新增 `jsonReadMemo`（按 `key` 缓存 `{ raw, value }`），当 `kvGet(key)` 返回的字符串引用与缓存一致时直接返回上次解析结果；`writeJson` 时立即更新/失效对应 `key` 的缓存。
- **验证结果**：同一轮渲染周期内多次调用 `getMixSession` / `loadMixCabinet` / `loadMixRecipes` 仅在底层字符串变更时解析 1 次。
- **遗留与风险**：调用方若原地 mutate 返回对象可能污染缓存，本模块写路径全部经由不可变展开（`{ ...session }`）后调 `writeJson` 刷新缓存。

## ③ 进对局卡 6–7s（第二层）：首帧前按窗口收拢轮次

- **现象**：进入 400+ 轮对局时首帧仍出现 2s+ 长任务。
- **实测数据**（源头仓库基准，415 轮对局）：进入对局单条长任务从 2227ms 降至 344ms。
- **根因**：`hiddenTurnCount` 原先初始值为 `useState(0)`，等到 `useLayoutEffect` 才调用 `setHiddenTurnCount` 收拢，导致首次渲染第一遍仍将全部 415 轮及挂载的沙盒 iframe 全量 map 进 DOM，随后立刻同步卸载重渲。
- **改了哪里**：
  - `components/mixology/mixology-game.tsx`（第 215–221 行）：`hiddenTurnCount` 的 `useState` 初值改为惰性初始化 `() => Math.max(0, (session?.turns.length ?? 0) - MIX_INITIAL_TURNS)`，确保首帧首次渲染即只切片最新 12 条。
- **验证结果**：首帧直接只渲染最新 `MIX_INITIAL_TURNS`（12）条记录。
- **遗留与风险**：无。

## ④ 对局内点跳转卡 2–4.3s：两头都有闸门的有界窗口

- **现象**：在长对局内跳转到早期轮次（如第 1 轮）时主线程阻塞 2–4.3s。
- **实测数据**（源头仓库基准，126 轮与 415 轮对局）：
  - 改动前：126 轮局跳第 1 轮渲染全部 126 行 + 68 个沙盒 iframe，单条 longtask 1973ms（真机 2026–4346ms，`sl≈duration`）。
  - 改动后：126 轮局跳第 1 轮仅渲 12 行 / 336ms；415 轮局跳第 1 轮仅渲 12 行 / 126ms；点击「查看更新的」12→24 行、404ms、首行不跳动；点击「回到最新」→ 12 行 / 165+139ms。
- **根因**：只收头部 `hiddenTurnCount` 而不限制尾部时，跳回第 1 轮会把第 1 轮到最新一轮全部铺进 DOM。
- **改了哪里**：
  - `components/mixology/mixology-game.tsx`（第 215–225、570–665、1220–1280 行）& `styles/mixology.css`（第 1320–1415 行）：
    - 新增尾部收起数 `hiddenTailCount`，渲染切片改为 `session.turns.slice(hiddenTurnCount, session.turns.length - hiddenTailCount)`；
    - 新增 `jumpToTurnIndex`：目标已在当前窗口内时直接平滑滚动；在窗口外时将窗口搬至目标处（目标前留 2 条、共 12 条），未渲染后文记入 `hiddenTailCount`，延迟 260ms 滚动并高亮目标行；
    - 底部新增常驻可见按钮「查看更新的 N 条 · 还有 M 条」与「回到最新」（同时清尾 + 收头 + layout effect 钉底）；
    - 贴底状态（`stickRef.current === "bottom"`）下钳位逻辑强制 `hiddenTailCount = 0`，确保新生成回合正常渲染；切换 `sessionId` 时重置 `hiddenTailCount = 0`。
- **验证结果**：任意跨度跳转均严格限制在 12 条窗口内，底部按批展开与一键回到最新均維持有界 DOM 规模。
- **遗留与风险**：跳转后延迟 260ms 滚动依赖沙盒首波高度回报，极端慢速设备上可能仍有轻微二次微调。

## ⑤ 退出时等待遮罩（「正在返回…」）

- **现象**：慢速设备或重度页面点击返回时，主线程被占用期间界面无反馈，用户分不清是没点上还是在加载。
- **实测数据**（源头仓库真机 Android WebView）：点击返回后 403–700ms 正常触发合成器线程淡入与 `transitionend`；快设备（<220ms 完成切换）零闪烁。
- **根因**：React 的 `onClick` 需等 `pointerup` 后才执行且同步提交阻塞主线程，期间主线程无法绘制新 UI。
- **改了哪里**：
  - `components/desktop-shell.tsx`（第 1125–1205、4895 行）& `styles/phone-shell.css`（第 1005–1040 行）：
    - 在 `pointerdown` 捕获阶段命中返回/关闭按钮时立即给 `.phone-return-mask` 挂 `.is-pending`；
    - CSS 设置 `transition: opacity 160ms ease 220ms` 跑在合成器线程；
    - 收回判定采用 `click` 后双 `rAF`（主线程阻塞期间帧不推进，两帧到达时若仍未退回桌面则立即移除类名，未满 220ms 故应用内返回不会闪）+ 400ms / 1200ms / 10s 三层墙上时钟兜底；
    - 文案采用中性「正在返回…」。
- **验证结果**：应用内返回不误闪，慢速退回桌面平稳浮现提示并在就绪后自动消失。
- **遗留与风险**：通过 `aria-label` / `title` 启发式识别返回键，自定义无障碍标签的私有返回键不会触发遮罩（不影响功能）。

## ⑥ 开机页死在「加载中」：首帧资源预热限时放行

- **现象**：部分 Android WebView 或后台冷启动场景下，开机 Splash 页进入按钮长期处于禁用（加载中）状态。
- **实测数据**：后台不可见状态下 `img.decode()` 永不 resolve；加 1500ms `Promise.race` 后最迟 1.5s 必定放行。
- **根因**：`components/main-app.tsx` 的 `prepareDesktopThemeForFirstPaint()` 无超时保护，直接 `await Promise.all(Object.values(assets).map(preloadImageDataUrl))`。
- **改了哪里**：
  - `components/main-app.tsx`（第 221–235 行）：引入 `FIRST_PAINT_PRELOAD_TIMEOUT_MS = 1500`，用 `Promise.race([..., wait(1500)])` 限时放行。
- **验证结果**：即使图片解码或资源读取挂起，1500ms 后开机页进入按钮必定可用。
- **遗留与风险**：极端慢速读取下桌面首帧可能出现一次壁纸/图标皮肤补绘重排，不影响数据安全。

## 踩过的坑备忘
1. **后台页帧率与解码假死**：`document.hidden` 为真时 `rAF` 不触发、`img.decode()` 永不 resolve，任何预热阻塞与动画回收都必须配墙上时钟兜底。
2. **`IDBObjectStore.prototype.put` 参数个数**：猴子补丁拦截 IDB `put` 时必须用 `original.apply(this, arguments)` 原样转发，写成 `call(this, value, key)` 会把单参调用变成显式传 `undefined` 引发 Dexie `DataError`。
3. **「回到最新」只清尾不收头**：如果只把 `hiddenTailCount` 置 0 而不把 `hiddenTurnCount` 收拢回 `total - 12`，会把跳第 1 轮后的 400 多轮瞬间全量铺进 DOM 造成 2s+ 回归。
4. **返回遮罩用固定 500ms 定时器抢跑收回**：真机 React 提交耗时 600ms+ 时，500ms 墙上定时器会抢在提交完成前把遮罩关掉，必须用 `click` 后双 `rAF` 让主线程忙完再判。
