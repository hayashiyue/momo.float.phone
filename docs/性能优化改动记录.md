    - **教训一：不要在已经叠了多层私改的链路上继续加定时器与重试**。v24 加的 `scheduleIdleBailoutRefresh`（15 秒防抖 + 10 秒重试 3 次）与 `refreshScheduledBailouts` 的 2.5 秒间隔循环，在全量提示词组装的量级下，恰好把「卡一下」放大成「卡—不卡—卡—不卡」的周期性卡顿。而让这套循环真正生效的，是同一次提交里刚接通的全局生成锁。
    - **教训二：`hasActiveGenerationLock` 长期是死代码**。`generation-lock.ts` 自建立起只有调用方没有 `beginGeneration()`，计数恒为 0。任何基于它的退避逻辑在接通前都不会生效，接通后会突然改变全部后台任务的行为——这类「隐形开关」在改动前必须先确认它是否真的在工作。
    - **教训三：删除定义必须同步清理全部调用，删除调用必须同步清理 import**。本轮多次出现「删了 `resolveShortTermMaxMessagesPerSession` 定义却留着 4 处调用」「删了 import 却留着函数体调用」的情况，每一次都会让整个项目在构建时失败。
    - **教训四：`edit_item` 的 find 片段中严禁写省略占位符**（如 `// ... (省略部分注释)`）。这类占位符永远匹配不到原文，会导致「工具返回成功但文件根本没改」，而后续汇报会误以为已生效。
    - **教训五：跨轮中断或取消提案后，暂存区已重置**。必须在同一轮内重新补齐全部待改文件，并核对提案卡片包含的文件个数。本轮曾出现过「9 个文件的提案里漏了 5 个已撤回的文件」的情况。
    - **当前状态**：`macro-engine.ts`、`prompt-sanitizer.ts`、`llm-http.ts`、`llm-prompt-assembler.ts`、`chat-engine.ts`、`group-chat-engine.ts`、`follow-up-service.ts`、`push-bailout-client.ts`、`push-outbox-client.ts`、`chat-room.tsx`、`dwelling-engine.ts`、`custom-app-host-api.ts` 均已恢复官方原样。保留的私改只有：开屏水合优化、API 列表排序（`api-groups.ts` 等）、保活音频不抢系统音频焦点（`use-weixin-bridge.ts`）。
    - **未还原项**：`lib/short-term-assembler.ts` 的 `prepareShortTermContext` 仍保留 v19 引入的单趟 `bucket` 分桶（等价于原来的约 20 次 `timeline.filter`，纯减少遍历次数，不改变输出）。若后续需完全对齐官方，可单独还原此段。

`macro-engine.ts`：`expand()` 加入口 `!text.includes("{{")` 短路；`postProcessTrim` 加 `!text.includes(TRIM_SENTINEL)` 短路。

### 5. 请求体序列化后立即解绑

`llm-http.ts`：`JSON.stringify(payload.body)` 之后 `payload.body = {}`。

### 6. 排序完善

- `binding-manager.tsx`：世界书、预设、正则、语音、身份五类选项补上 `sortOptions`（走 `compareLabelAsciiFirst`，遵循 `loadApiSortMode()` 模式）。

### 本轮踩过的坑

1. **改本文档只能用「编辑」找锚点追加，绝不能用「写入」**——「写入」是整份替换，27 轮历史会全丢（本轮已发生过两次）。repo 类型的 `append` 参数不生效。
2. **删除函数/常量定义前，必须先把全项目所有调用处改完**。第 27 轮 `MACRO_ALREADY_EXPANDED_MARKERS` 就是常量删了三处调用还在，角色直接发不出消息。
3. **`forEach` 改 `for` 时，体内 `return` 必须逐个改成 `continue`**，否则整个生成器提前结束、历史消息静默截断。
4. **不要擅自清空暂存区**。为修一份文档清空整个暂存区，会连带毁掉十来个已改好的文件（本轮已发生过）。

6. **不要接通长期是死代码的开关**。`generation-lock` 的 `beginGeneration` 从未被调用，第 28 轮一接通，配套的退避重试立刻开始工作，造出「卡 1～2 秒、不卡、循环三四次」的周期卡顿。

## 五、第 30 轮修复（SW v31）

第 29 轮（v30）上线后故障比改之前更严重：生成一卡一顿、挂后台重载、聊天室等生成闪退、吐字到一半调工具闪退、切后台重载后开屏箭头不出来、重启手机白屏。逐行复核后确认第 29 轮留下三类硬伤，本轮全部修掉。

### 1. 线上四处未声明标识符（硬崩溃，最高优先级）

第 29 轮「还原至官方原版」时删了声明，调用点没清干净，线上直接抛 ReferenceError：

- `lib/push-outbox-client.ts`：`consumeServerOutbox` 里的 `preMergeSessionBaseline.clear()` 与 `consumedOutboxIdSet.has(entry.id)`，两个标识符在 327 行里都没有声明。`env_check` 已实锤抓到 `Can't find variable: preMergeSessionBaseline`。函数在进 `try` 之前就抛错，离线回传合并整条瘫痪（冷启动 / 回前台拉云端消息必挂）。两处调用连同注释一并删除，退回官方「按 `armAt` 与 `followUpIndex` 判重」的路径。
- `lib/llm-prompt-assembler.ts` 群聊分支 `assembleGroupPromptPayload`：`renderJoined` 里调用了不存在的 `joinWorldBookEntriesWithMacros`（真实定义是 `joinWorldBookEntries`，v30 改名时群聊调用点漏改）。群聊只要命中一本绑定给 ≥2 名成员的共享世界书，整轮生成直接 ReferenceError。
- `lib/llm-prompt-assembler.ts` 群聊 `<member>` 块：`MACRO_ALREADY_EXPANDED_MARKERS.has(p.identifier)`，该常量第 27 轮已删除，单聊改成了显式判断，群聊漏改。现按 `p.identifier !== "worldInfoBefore" && p.identifier !== "worldInfoAfter"` 判定，**不引入任何新常量**。

### 2. `chat-engine.ts` 后台兜底：撤销 v30 的「即时监听」

v30 把原来的 15 秒延迟改成「一进生成就挂 `visibilitychange` 监听 + 每 1.5 秒 `setInterval` 巡检」，后果是：

- 用户一划走切后台，回调在毫秒级触发，正好撞上 iOS 已把后台内存配额压到最低的瞬间，同步克隆整份 `llmMessages` + `buildProviderRequest`（内部含 `JSON.stringify`）上传，被 Jetsam 杀进程重载——即「生成中挂后台，切回来整页重新加载」；
- 那个闭包在整个生成与多轮工具调用期间钉住原始 `llmMessages`、`regexes`、`preset` 不让 GC，与流式缓冲、工具轮次请求体三份同时驻留，把「聊天室等生成」「吐一半调工具」顶爆闪退。

现改为：`ReplyBailoutRef` 增加可选 `cancelPending?: () => void`；`generateChatCompletion` 的 `finally` 里先 `cancelPending?.()` 再 `settle()`；兜底段只登记**单次 15 秒 `setTimeout`**，到点后依次校验 `closed / superseded / signal.aborted / document.hidden`，全部通过才让出一帧并组装上传。普通回复几秒内就结束、定时器在 `finally` 里立刻撤掉，全程零额外开销。

### 3. 三处后台全量组装改为远离前台窗口

`armIdleReconnectBailout` / `armFollowUpBailout` / `runSync` 内部都是完整 `buildChatPromptMessages` + 双份 `buildProviderRequest` + 800KB 级 JSON 序列化，属于重活：

- `lib/follow-up-service.ts` `scheduleIdleReconnectArm`：防抖 8 秒 → **45 秒**。8 秒在正常打字节奏（间隔普遍超过 8 秒）下几乎每句话都会到点，正好撞在流式吐字与工具轮次上，这是「不卡—卡—不卡」周期卡顿的直接来源。同时触发前增加 `firingSet.has(sessionId) || backgroundGeneratingSessions.has(sessionId)` 守卫。
- `lib/follow-up-service.ts` `scheduleFollowUp`：注释写着「延后一拍让出渲染帧」，实际是同步 `void armFollowUpBailout(...)`，每条回复都白跑一次全量组装。改为新增 `followUpArmTimers` 模块级 Map，**2.5 秒防抖**（`FOLLOWUP_ARM_DEBOUNCE_MS`），触发前校验页面可见、非生成中、且该轮排期仍在（防止防抖期间用户已回复/取消）；`cancelFollowUp` 开头调用 `clearFollowUpArmTimer` 撤掉挂起项。
- `lib/push-bridge-sync.ts`：`CHAT_MESSAGE_PUSHED_EVENT` / `CHAT_MESSAGES_DELETED_EVENT` / `chat-messages-updated` 三个监听由 `scheduleSync(3_000)` 改为 **25 秒**。`runSync` 的内容指纹比对排在全部快照组装**之后**，指纹命中只省网络、不省组装；聊天热络时每句话都会重跑一遍全量快照。`reality-bridge-rules-updated` 保持 3 秒不变（低频、且是真配置变更）。

### 4. 世界书逐条展开不再放大正则遍历

`joinWorldBookEntries`（v30 新增）为了用 `expand` 入口的 `includes("{{")` 短路，把 `applyWorldInfoRegex` 也塞进了逐条循环，规则遍历次数从「规则数」放大成「条目数 × 规则数」，且 `runRegexRule` 的 replace 回调里每次命中都重建替换串并跑宏展开。

现改为：循环内**只做宏展开**，`join` 之后对整串统一跑一次 `applyWorldInfoRegex`（空串或无规则直接返回）。既保留短路收益，又完全还原官方「整块跑一次」的正则语义。

### 5. 首屏箭头不出来 / 重启白屏

- `public/sw.js`（`CACHE_VERSION` → `ai-phone-pwa-v31`）：activate 阶段原顺序是「先把所有旧缓存桶删光 → 再 `cache.add("/")` 且失败被 `catch` 吞掉」。若那一刻网络不通，新桶没写进去、旧桶已删净，之后冷启动 `networkFirst` 既无缓存也无网络，根导航 `throw` → **白屏**。现改为四步：① 先从旧桶里抓现成的 `"/"` 作兜底种子；② 确保当前版本静态桶里确实存有 `"/"`（拉取失败则用种子 `put`）；③ 确认可用后才删除旧桶（连种子都没有时**不删**，留待下次激活重试）；④ 只 `clients.claim()`，**删除 `client.navigate` 循环**——它和 `components/pwa-registrar.tsx` 的 `window.location.reload()` 会在同一毫秒级窗口并发两条导航，iOS WebKit 上互相打断，表现为「切回来一直重新加载」。
- `components/main-app.tsx`：新增 `THEME_PRELOAD_TIMEOUT_MS = 2500`，用 `Promise.race` 包住 `prepareDesktopThemeForFirstPaint()`。`getThemeAssetMap` 内部是只挂 `onsuccess/onerror` 的 IndexedDB 请求，没有任何超时出口；iOS 从后台恢复或整页重载瞬间连接可能挂起不回调，`await` 永不返回 → `setHydrated(true)` 永不执行 → 开屏「进入主页」箭头永不出现。正常启动几十毫秒返回，超时返回 `null` 直接放行（`DesktopShell` 会在挂载后经 `initialThemeAssets` 增量 effect 补齐资产，不牺牲正确性）。

### 6. 工坊（小坊）发送卡顿

- `lib/qa-chat-store.ts`：`sendQaMessage` 里第二次 `emit()` 改为 `emit(true)`，跳过对整段上下文的字符累加重算（预算 100 万字符、条目上千时这一遍并不便宜）；让帧改为 `requestAnimationFrame` + 60ms `setTimeout` 双出口等待，确保用户气泡先上屏再做请求体组装与序列化（只用 rAF 会在「点完发送立刻切后台」时被 iOS 冻结回调，把整轮永久卡在生成中）。
- `lib/qa-agent-engine.ts`：新增 `QA_LOG_MSG_MAX_CHARS = 12_000` 与 `clipLogContent`，在 `logQaCall` 与流式失败降级的那条 `pushApiLog` 两处对超长正文做头尾截断。工坊常年贴几十万字符源码，整包进日志环会与请求体、流式缓冲三份同时驻留。聊天引擎四条路径早就这么做了，工坊这两处一直漏着。

### 7. 工坊四项偏好被「清缓存」悄悄重置回默认

现象是「小坊上下文上限总是自己变回 1000000」。根因不在默认值写死，而在**存储位置**：`ai_phone_qa_context_budget_chars`（`lib/qa-chat-store.ts`）与 `ai_phone_qa_page_chars` / `ai_phone_qa_max_output_tokens` / `ai_phone_qa_max_rounds`（`lib/qa-prefs.ts`）这四项，此前只写裸 `localStorage`，既没有 IndexedDB 副本可恢复，也没有在 `lib/data-management/modules.ts` 的主模块登记。于是它们落进 `cache` 模块的 `includeAll` 范围——用户点一次「缓存与未分类数据 → 清理」，或恢复一份不含缓存的备份，四项设置连同其它遗留键一起被删，下次读取直接回落到默认值。

现改为：

- `lib/qa-prefs.ts`：新增 `readPref` / `writePref` 两个小助手（`kvGet` 优先、`localStorage` 兜底），四项全部改走 kv-db，并对各自的键调用 `registerKvMigration` 迁移旧值；写入改 `kvSet`、恢复默认改 `kvRemove`。
- `lib/qa-chat-store.ts`：`getContextBudget` / `setQaContextBudgetChars` 同样改走 kv-db + `registerKvMigration`，并保留 localStorage 兜底读。`setQaContextBudgetChars` 末尾保持 `emit()` 不变——`contextUsage` 是「已用 / 预算」的比值，必须按新分母重算才会更新进度条，传 `emit(true)` 会沿用旧比值导致保存后百分比不动。
- `lib/data-management/modules.ts`：把四个键登记进 `settings` 主模块的 kv `keys`。这一步和迁 kv-db 缺一不可：只迁 kv-db 而不登记，`cache` 模块照样会把它们扫进清理范围；只登记而不迁，旧值仍然只有 localStorage 一份副本。

### 本轮新增教训

7. **「还原至原版」是最危险的操作，必须逐调用点核对**。第 29 轮声称还原，实际留下四处未声明标识符（两处在离线回传、两处在群聊组装），全部只在运行时才炸，构建期毫无提示。删任何声明前，先全库搜调用点，删完再搜一次确认归零。
8. **不要用「立刻监听 + 定时巡检」替代延迟**。v30 把 15 秒延迟换成即时 `visibilitychange` 监听，等于把重活精确挪到了「切后台瞬间」这个内存配额最低的时刻，比原来的延迟更糟。异步兜底类逻辑，宁可晚、不可抢在页面状态切换的瞬间执行。
9. **防抖时长要按真实用户节奏定，不能只为「不阻塞当前帧」**。8 秒防抖在正常打字节奏下形同虚设（每条消息后都会触发一次），必须放宽到远超人类操作节奏的量级（45 秒），并叠加「正在生成/页面隐藏」双守卫。
10. **Service Worker 的 activate 必须「先建立新的安全兜底，再清理旧的」**。任何「先删后拉」的顺序在网络失败时都会把用户推进无缓存深渊，且 `catch` 吞掉失败会让问题完全静默。
11. **任何 `await` 在开屏关键路径上都必须有超时**。IndexedDB 请求只有 `onsuccess/onerror` 两个出口，iOS 上连接挂起时不回调，一个没有超时的 `await` 就能让开屏永久停住。
12. **指纹缓存/内容哈希类「跳过上传」优化，救不了组装开销**。若指纹比对排在组装之后，它只省网络流量；真正的开销在组装本身，必须靠防抖与守卫来控制触发频率。
13. **用户可调的设置项不能只写裸 `localStorage`**。「缓存与未分类数据」模块是 `includeAll` 的兜底清理器，任何没在主模块登记的键都会被它扫走；而 localStorage 本身在 iOS 上也没有 IndexedDB 那样的持久化保障。凡是用户能在界面上调的项，一律走 kv-db + `registerKvMigration`，并在 `lib/data-management/modules.ts` 的主模块里登记键名——两件事缺一不可，只做一半仍然会丢。
14. **`requestAnimationFrame` 不能单独当作「让出一帧」的同步点**。页面一进后台，iOS 会冻结 rAF 回调，只靠 rAF 的 `await` 会永久挂起，把整条流程卡在中间状态（生成中、忙碌标志不复位）。凡是跨越「用户点完立刻切后台」这个窗口的让帧等待，都要配一个 `setTimeout` 兜底出口。
